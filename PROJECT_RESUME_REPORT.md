## 0. Границы достоверности

Проект представляет собой MVP веб-приложения для подготовки договоров DOCX на основе реквизитов клиента, условий договора и Excel-сметы. Наиболее содержательная часть проекта: backend-сценарий обработки сметы и генерации документов, связанная модель данных и интерфейсы истории.

В этом отчёте используются следующие статусы:

| Статус | Значение |

| Реализовано | Найден конкретный исполняемый код. Это не подтверждение успешного запуска во всех окружениях. |
| Внедрено | Есть доказательства использования в рабочей среде. По доступным материалам этот статус не подтверждён ни для одной функции. |

Исследована ветка `DG-1`, текущий HEAD: `6ada7b6`. Относительно локального указателя `origin/DG-1` ветка опережает его на один коммит; состояние удалённого сервера не запрашивалось. Каталог шаблонов и связанные изменения frontend/backend присутствуют в незакоммиченной рабочей копии, включая новые маршруты `/templates` и `/templates/[id]`. Поэтому отчёт описывает рабочую копию, а не только последний коммит.

Тесты, сборка, Docker и приложение в ходе анализа не запускались; к рабочей БД подключения не было. Фактическое число записей и успешность пользовательских сценариев в текущем окружении не проверены. Секретные `.env` не открывались. JSON-манифесты и lock-файлы исключены из анализа по правилам проекта, поэтому точные версии большинства пакетов и полный набор npm-скриптов не устанавливались. Обход репозитория рекурсивным сканированием не выполнялся; отсутствие технологии означает отсутствие подтверждения в исследованных компонентах.

## 1. Назначение проекта

**Название:** Document Generator / `document-generator`.

**Основная задача:** сформировать договор на оказание услуг из подготовленного Word-шаблона, заполнив реквизиты, финансовые условия, сроки и таблицу работ из Excel-сметы, затем сохранить договор и результат генерации для последующего просмотра и скачивания.

В коде предусмотрены договоры трёх направлений: CRM, разработка сайта и обучение; заказчики двух юридических типов: ООО и ИП; одна или две оплаты. Это классификация договоров на услуги, а не реализация собственной CRM-системы.

**Предполагаемая аудитория:** сотрудники, которые подготавливают договоры по клиентским проектам, например менеджеры и специалисты по документообороту. Конкретные должности и организация-заказчик из материалов достоверно не установлены. Разделение интерфейса по ролям отсутствует.

**Процесс до автоматизации:** по назначению функций можно восстановить набор ручных операций: выбор Word-шаблона, перенос реквизитов, перенос работ из Excel, расчёт предоплаты и остатка, заполнение суммы прописью, присвоение номера и сохранение файла. Это обоснованное описание заменяемых операций, но не подтверждённое исследование исходного процесса конкретной компании.

**Практическая польза:** сотрудник вводит данные один раз в рамках заявки, прикладывает смету и получает заполненный документ. Система хранит связь клиента, договора, шаблона и генераций, что позволяет найти документ позднее. Экономия времени и снижение ручных ошибок ожидаемы по устройству сценария, но количественно не измерены.

Подтверждения: [ContractsService](backend/src/contracts/contracts.service.ts), [форма](frontend/src/features/create-document/CreateDocumentForm.tsx), [схема БД](backend/prisma/schema.prisma).

## 2. Реализованный функционал

### 2.1. Подготовка договора через веб-форму

**Реализовано.** Пользователь выбирает направление договора, юридический тип заказчика, вариант оплаты, наличие ТЗ; заполняет реквизиты, подписанта, дату, город и сроки; прикладывает `.xlsx`.

Форма условно показывает КПП/ОГРН для ООО, ОГРНИП для ИП, проценты для двойной оплаты и сроки ТЗ при включённом ТЗ. Обязательные HTML-поля отмечаются `*`; во время отправки кнопка блокируется, показывается индикатор. При успехе выводится ссылка на DOCX, при ошибке отображается сообщение backend или сетевой ошибки.

Город по умолчанию: `г. Пенза`. Гарантийный срок в форме: `1 месяц`; он передаётся и для TRAINING. Переключение светлой/тёмной темы относится к форме.

Переключение направления применяет три пресета: `crm_ooo_double`, `site_ip_single_tz`, `training_ooo_single` с соответствующими параметрами. Код шаблона находится в frontend-маппинге, а не вычисляется динамически из актуального каталога БД. Пользователь может затем отдельно изменить юридический тип, оплату или ТЗ, при этом `templateCode` не пересчитывается. Поэтому соответствие произвольной комбинации параметров шаблону пока не обеспечено полностью.

Подтверждение: [CreateDocumentForm.tsx](frontend/src/features/create-document/CreateDocumentForm.tsx).

### 2.2. Единый API полного цикла

**Реализовано.** `POST /contracts/full-generate` принимает multipart-запрос: строку JSON в поле `payload` и Excel в поле `file`.

Фактический порядок в сервисе: создание/получение клиента, определение шаблона, парсинг сметы, создание договора, повторный парсинг и привязка сметы, генерация DOCX. Ответ содержит `contractId`, `generationId`, `fileName`, `downloadUrl`.

Это избавляет frontend от координации нескольких последовательных запросов. Одновременно весь процесс остаётся внутри одного HTTP-запроса; очереди и отдельного worker нет. При ранней ошибке уже созданный клиент может остаться в БД.

Подтверждения: [контроллер](backend/src/contracts/contracts.controller.ts), [сервис](backend/src/contracts/contracts.service.ts), [frontend API](frontend/src/shared/api/contracts.api.ts).

### 2.3. Хранение и повторное использование клиентов

**Реализовано на backend.** CRUD API клиентов хранит реквизиты организации/ИП, адреса, банковские данные и сведения о подписанте. Full-generate принимает либо `clientId`, либо данные нового клиента.

Через API можно использовать существующего клиента. Текущая форма каждый раз передаёт объект нового клиента; выбора из справочника в ней нет. Поиск дублей по ИНН и уникальность ИНН в схеме не реализованы. Пункт Clients в sidebar ведёт на главную, отдельного готового клиентского справочника в исследованном UI нет.

Подтверждения: [ClientsController](backend/src/clients/clients.controller.ts), [ClientsService](backend/src/clients/clients.service.ts), [ContractsService](backend/src/contracts/contracts.service.ts), [Sidebar](frontend/src/widgets/sidebar/Sidebar.tsx).

### 2.4. Разбор Excel-сметы

**Реализовано.** Парсер читает первый лист `.xlsx`, ищет заголовки по текстовым признакам, определяет колонки работ, часов, денег и этапов. Дополнительно извлекает метаданные проекта, аналитика, менеджера, даты оценки, ставки и проверки архитектора.

Для каждой работы собираются название, этап, часы по видам деятельности, общие часы и стоимость. Пустые строки, строки итогов и строки без положительных часов/стоимости исключаются. Значения ячеек преобразуются из чисел, строк, rich text и сохранённых результатов формул.

Работы группируются по этапам. При отсутствии этапов создаётся общий этап «Работы по проекту» и предупреждение. Итоги вычисляются по строкам; расхождение с суммой/часами в шапке фиксируется предупреждением с допуском `0.01`.

**Ограничения:** поддерживается узнаваемая структура русскоязычной сметы, а не произвольный Excel. ExcelJS здесь читает сохранённый результат формулы; отдельного вычислителя формул нет. Предупреждения не блокируют создание договора. Нераспознанное число может превратиться в ноль, поэтому строгой финансовой валидации произвольных входных данных нет.

Подтверждения: [ExcelEstimateParser](backend/src/estimates/parsers/excel-estimate.parser.ts), [EstimatesService](backend/src/estimates/estimates.service.ts).

### 2.5. Суммы и условия оплаты

**Реализовано.** Сумма договора берётся из рассчитанного итога сметы. Для двойной оплаты проверяется, что предоплата и постоплата вместе составляют 100%. При привязке сметы сумма и части оплаты пересчитываются.

В БД денежные поля используют `Decimal(12,2)`. В прикладном коде вычисления выполняются через JavaScript `number`; это не сквозная decimal-арифметика. Есть собственный перевод суммы в русские слова и форматирование денежных значений для документа.

Подтверждения: [ContractValidationService](backend/src/contracts/services/contract-validation.service.ts), [ContractsService](backend/src/contracts/contracts.service.ts), [moneyToWords](backend/src/shared/helpers/number-to-words.helper.ts), [schema.prisma](backend/prisma/schema.prisma).

### 2.6. Автоматическая нумерация

**Реализовано.** Номер имеет формат `ДДММГГГГ-порядковыйНомер`. Для даты хранится отдельный счётчик `ContractCounter`; номер получается через Prisma `upsert` с `increment`. Поля `dateKey` счётчика и `Contract.number` уникальны.

Нумерация перенесена из ручной работы в БД. При этом выделение номера не объединено с созданием договора в общую транзакцию: после ошибки возможны пропуски. Нагрузочная проверка конкурентного создания не проводилась в рамках анализа.

Подтверждения: [ContractNumberService](backend/src/contracts/services/contract-number.service.ts), [schema.prisma](backend/prisma/schema.prisma).

### 2.7. Подбор и каталог шаблонов

**Реализовано.** Backend выбирает шаблон в порядке `templateId`, затем `templateCode`, затем по `type/legalType/paymentType/hasTz` с `isActive=true`. Если переданный code не найден, возвращается ошибка; к поиску по комбинации в этом случае сервис не переходит.

В текущей рабочей копии `GET /templates` возвращает все записи, включая неактивные, с параметрами и признаком наличия файла. Есть `GET /templates/:id`, таблица `/templates` и страница деталей. Главная загружает список из API и отмечает inactive бейджем.

**Ограничения:** главная показывает элементы каталога без ссылки на детали; открыть карточку можно из таблицы `/templates`. Загрузка и редактирование шаблонов через UI отсутствуют. Поиск по явному id/code не проверяет `isActive`, поэтому inactive не запрещён как источник генерации на уровне backend.

Seed содержит три записи: `crm_ooo_double`, `site_ip_single_tz`, `training_ooo_single`. Код списка позволяет показать четвёртый `test_contract`, если он есть в БД, однако ни его наличие, ни общее число записей в рабочей БД не подтверждены.

Подтверждения: [TemplatesService](backend/src/templates/templates.service.ts), [seed.ts](backend/prisma/seed.ts), [DashboardHome](frontend/src/app/DashboardHome.tsx), [таблица](frontend/src/app/templates/page.tsx), [детали](frontend/src/app/templates/[id]/page.tsx).

### 2.8. Генерация DOCX

**Реализовано.** Сервис получает договор со связанными клиентом и шаблоном, проверяет доступность файла, строит словарь плейсхолдеров и заполняет DOCX.

`DocumentContextBuilder` готовит реквизиты, дату по-русски, суммы числом/прописью, предоплату, остаток, сроки услуг, ТЗ, гарантии, таблицу работ и общие итоги. Таблица строится из сохранённых этапов `estimateJson`, имеет сквозную нумерацию строк.

`DocxTemplateRenderer` использует docxtemplater с `{{...}}`, повторяющимися блоками и переносами строк. DOCX читается и собирается как ZIP через PizZip. После рендера проверяются XML-файлы внутри `word/`: при найденных незаменённых плейсхолдерах выбрасывается ошибка.

**Ограничения проверки:** отсутствующее значение context builder часто заменяет пустой строкой. Поэтому документ без `{{...}}` может содержать пустой обязательный фрагмент. Поиск регулярным выражением в XML также не является полной проверкой всех случаев разделения тегов Word-разметкой. Полноту и юридическую корректность документа эта проверка не гарантирует.

Подтверждения: [DocumentsService](backend/src/documents/documents.service.ts), [DocumentContextBuilder](backend/src/documents/builders/document-context.builder.ts), [DocxTemplateRenderer](backend/src/documents/renderers/docx-template.renderer.ts).

### 2.9. История и скачивание

**Реализовано.** Для запуска рендера создаётся `Generation` со статусом PROCESSING и снимком context в `sourceDataJson`. После записи файла статус становится SUCCESS; при пойманной ошибке рендера/сохранения становится FAILED с сообщением.

`/contracts` показывает договоры, клиентов, суммы, шаблоны и последний успешный результат. `/contracts/[id]` показывает основные условия, клиента, сводку сметы и связанные генерации. `/generated` показывает историю со статусами, именами файлов и ошибками; SUCCESS можно скачать через `GET /generations/:id/download`. Ошибка FAILED выводится в таблице, отдельное окно просмотра не реализовано.

Есть backend preview `GET /documents/:contractId/preview`, возвращающий подготовленный context; это не визуальный просмотр DOCX/PDF. Редактирование и удаление договоров есть в API, но не в страницах истории.

**Важное ограничение:** имя файла зависит только от номера договора. Повторная генерация того же договора записывает файл по тому же пути, а старые Generation могут указывать на обновлённый файл. Реализована история попыток, но не независимое хранение версий DOCX. Ошибки до создания PROCESSING, например отсутствие файла шаблона, не сохраняются как FAILED в этой цепочке. Аварийное завершение процесса может оставить PROCESSING.

Подтверждения: [GenerationService](backend/src/generations/generation.service.ts), [download controller](backend/src/generations/generation.controller.ts), [DocumentsService](backend/src/documents/documents.service.ts), [договора](frontend/src/app/contracts/page.tsx), [карточка](frontend/src/app/contracts/[id]/page.tsx), [генерации](frontend/src/app/generated/page.tsx).

### 2.10. Dashboard и вспомогательные возможности

**Реализовано.** `GET /dashboard/stats` параллельно считает клиентов, договоры, активные шаблоны и успешные генерации. Главная повторно запрашивает stats после успешной отправки формы без перезагрузки страницы.

Количество шаблонов в метрике означает только active, тогда как каталог показывает все записи. Значение 3 зависит от данных БД, а не зашито в endpoint. Ошибки загрузки stats/templates на главной сейчас подавляются: пользователь может увидеть начальные нули или пустой список при недоступном API.

Backend также содержит хранение настроек `AppSetting` и health-проверку БД через `SELECT 1`. Это технические возможности; полноценный UI настроек и система мониторинга не подтверждены.

Подтверждения: [DashboardService](backend/src/dashboard/dashboard.service.ts), [DashboardHome](frontend/src/app/DashboardHome.tsx), [SettingsService](backend/src/settings/settings.service.ts), [HealthService](backend/src/health/health.service.ts).

## 4. Архитектура и техническая сложность

### 4.1. Организация приложения

Backend устроен как модульный монолит NestJS. Controllers принимают HTTP, services координируют бизнес-операции, Prisma работает с PostgreSQL. В документной подсистеме выделены построение context, рендеринг и файловое хранение. Это полезное разделение ответственности: Word-теги не требуется формировать в UI, а Excel-парсер не отвечает за сохранение договора.

Frontend использует feature-oriented структуру `app/features/shared/widgets/entities`. Форма и dashboard являются client components; страницы истории получают данные на сервере Next.js. API-вызовы и форматирование вынесены в shared. Наличие папки `entities` не доказывает реализацию полноценного DDD.

Поток данных:

```text
React-форма + XLSX
  -> POST /contracts/full-generate
  -> клиент -> шаблон -> Excel-парсер -> договор
  -> сохранение estimateJson и пересчёт оплаты
  -> DocumentContextBuilder -> DocxTemplateRenderer
  -> локальный DOCX + Generation SUCCESS/FAILED
  -> downloadUrl, история, обновление dashboard
```

Подтверждения: [AppModule](backend/src/app.module.ts), [ContractsService](backend/src/contracts/contracts.service.ts), [DocumentsService](backend/src/documents/documents.service.ts).

### 4.2. Данные и целостность

В Prisma шесть моделей: Client, Template, Contract, Generation, ContractCounter, AppSetting. Связи: клиент имеет договоры; договор относится к клиенту и, опционально, шаблону; договор имеет множество генераций. В SQL заданы внешние ключи и уникальные индексы номера договора, кода шаблона, ключа настройки и даты счётчика.

`estimateJson` сохраняет результат разбора сметы без создания отдельных таблиц работ/этапов. `sourceDataJson` сохраняет данные, поданные в renderer. Это удобно для истории и диагностики, но не равнозначно неизменяемому аудиту: у снимков нет контроля целостности или отдельной системы версий.

`formDataJson` присутствует в схеме, но в исследованном create-потоке не заполняется. Сохранение оригинального XLSX в full-generate не реализовано: parser работает с buffer, сохраняется разобранная структура.

Единственная найденная миграция задаёт default города `Penza`; текущая Prisma-схема и backend default используют `г. Пенза`. Отдельной миграции изменения default не найдено. Реальный default в конкретной БД требует проверки.

Подтверждения: [schema.prisma](backend/prisma/schema.prisma), [миграция](backend/prisma/migrations/20260601094724_init_without_users/migration.sql), [ContractsService](backend/src/contracts/contracts.service.ts).

### 4.3. Авторизация и доступ

**В разработке.** AuthService проверяет только наличие email/password и выдаёт фиксированный development-токен. Проверки пароля по хешу, пользователей БД и подписанного access token в этом сервисе нет. UsersService возвращает пустой массив; модели User в текущей Prisma-схеме нет. Проверки ролей и guards на исследованных бизнес-контроллерах не обнаружены.

Эту часть нельзя описывать как реализованную JWT-авторизацию, RBAC или защищённое многопользовательское приложение. Наличие auth-модуля и JWT-конфига само по себе этого не подтверждает.

Подтверждения: [AuthService](backend/src/auth/auth.service.ts), [UsersService](backend/src/users/users.service.ts), [схема](backend/prisma/schema.prisma).

### 4.4. Ошибки, сбои и повторы

Есть прикладные проверки отсутствующего клиента/шаблона, некорректного JSON, расширения файла, структуры сметы и суммы процентов. Рендеринг логируется; ошибки после создания Generation сохраняются в FAILED и пробрасываются вызывающему коду.

Ограничения, которые необходимо учитывать при описании надёжности:

- Full-generate выполняет несколько независимых записей без общей транзакции или компенсирующего удаления. Возможны частично созданные данные.
- Нет idempotency key или защиты backend от повторной отправки. Блокировка submit помогает только в текущем UI; повтор запроса может создать клиента и договор снова.
- В full-generate JSON приводится к TypeScript-типу через `as`, но вложенные DTO не проходят явное `ValidateNested`/преобразование. Глобальный ValidationPipe не делает это приведение полноценной runtime-валидацией.
- Двойная оплата проверяется на сумму 100, но защиты всех входных полей full-generate одной этой проверкой не достигается.
- Отдельного восстановления зависших PROCESSING и автоматических retry нет.
- Имя повторно созданного DOCX не включает generationId, что допускает перезапись истории файлов.
- В multipart endpoint не задан явный предел размера загрузки. Большие XLSX/ZIP могут создавать нагрузку на память и CPU.

Это ограничения MVP, а не основание приписывать проекту реализованные механизмы отказоустойчивости.

### 4.5. Производительность и логирование

Подтверждённые решения: четыре независимых count в dashboard выполняются через `Promise.all`; для последнего успешного файла договора используются фильтр SUCCESS, сортировка и `take: 1`; Excel и файловые операции используют async API.

Async не означает фоновое выполнение: парсинг/рендеринг удерживают пользовательский запрос, а CPU-часть выполняется в процессе backend. В full-generate одна смета разбирается дважды. Списки без пагинации, а запросы истории могут возвращать крупные JSON-снимки вместе с сущностями. Нагрузочные характеристики не измерены.

Есть Nest Logger с префиксами этапов и frontend console.log. В контроллере логируется сокращённый payload; вместе с тем создание клиента выводит name/ИНН, а парсер выводит имя аналитика. Нельзя утверждать, что персональные данные полностью исключены из логов. Redaction, централизованный сбор, трассировка и retention policy не подтверждены.

HealthService проверяет доступность БД. Метрики dashboard являются бизнес-счётчиками, а не техническим мониторингом latency, ошибок и ресурсов.

### 4.6. Развёртывание и сопровождение

**Реализована конфигурация.** Dockerfile обоих приложений имеют этапы deps/build/runner. Backend генерирует Prisma Client и собирает NestJS. Compose описывает PostgreSQL 16, backend и frontend; для БД используется named volume, для документов bind mount `backend/storage`.

README описывает локальную разработку, генерацию клиента, Prisma migrate и Studio. Это подтверждает подготовку окружения, но не запуск в production. Compose не содержит healthcheck и автоматического применения миграций. Отдельного runbook резервного копирования, TLS, управления секретами и обновлений не обнаружено в изученных материалах.

Каталог шаблонов проверяет `storage.templatesPath`, тогда как config определяет `storage.templates`; генерация разрешает путь через `STORAGE_ROOT`. В нестандартном окружении проверка каталога и renderer могут смотреть в разные места. Это не устранённая архитектурная неопределённость.

Подтверждения: [Docker Compose](docker-compose.yml), [backend Dockerfile](backend/Dockerfile), [frontend Dockerfile](frontend/Dockerfile), [README](README.md), [storage config](backend/src/config/storage.config.ts), [LocalFileStorageService](backend/src/files/storage/local-file-storage.service.ts).

### Вариант А: четыре предложения

Document Generator — веб-приложение для подготовки договоров DOCX по реквизитам заказчика, условиям оплаты и Excel-смете. Backend на NestJS и PostgreSQL/Prisma связывает клиента, договор, шаблон и историю генераций; ExcelJS разбирает работы и этапы, а docxtemplater заполняет Word-документ. Frontend на Next.js/React предоставляет форму подготовки, историю документов и dashboard; решение автоматизирует перенос данных из сметы в договор, количественный эффект внедрения пока не установлен.

### Вариант Б: пять пунктов для раздела опыта

- Реализация REST-сценария подготовки договора: multipart-загрузка сметы, создание клиента и договора, подбор шаблона, генерация и скачивание DOCX.
- Разработка обработки XLSX-смет: определение колонок по заголовкам, извлечение работ и метаданных, группировка этапов, расчёт итогов и предупреждения о расхождениях.
- Реализация документной подсистемы с отдельными context builder и renderer: реквизиты, финансовые условия, сумма прописью, повторяющиеся строки работ и проверка остаточных тегов.
